:sect what
.title What
.p LSV (Line Separated Values) is a plain-text record format, similar in spirit to csv/tsv but line-marker based instead of delimiter based. It stores multi-line values with no escaping mechanism - no quoted fields, no backslash escapes - as long as one constraint holds: a value's own lines never begin with a colon or a dot (indent such lines by one space to keep them value text).

:sect tokens
.title Tokens
.p A token is ASCII alphanumeric, with optional embedded dots to separate words, and must begin with a letter.
:-------------------------------
:sect records
.title Records
.p A record is identified by LF:<typeCode> <attributes>, where typeCode must be a valid token. Any invalid typeCode is treated as a remark and ignored.
.p Reservation happens at two levels: the typeCodes below are reserved at the SYNTAX level, in every .lsv file; a schema like :DOC reserves further record codes and fields at its own SCHEMA level.
:def REM
.means reserved - remarks
:def DOC
.means reserved - a DOC header record (see DOC section)
:def AIDOC
.means reserved - an AI-generated/AI-maintained document (see AIDOC section)
:def LSV
.means reserved - tsv <-> csv <-> lsv reformatting
:-------------------------------
:sect fields
.title Fields
.p A field is identified by LF.<fieldName> <value up to next marker>. fieldName may be written quoted (LF."field name", matching a csv column header) or as a bare token when the header is itself a valid token.
:-------------------------------
:sect comments
.title Records as comments or separator bars
.p Any record whose typeCode isn't a valid token is a COMMENT RECORD - ignored as content while still acting as a record boundary: it terminates the record before it, which is why a comment or bar sits between records, never between the fields of one record.
.p Conventional prefixes: :// (comment text, code-style), :== (major separation bar), :-- (sub separation bar), :REM (the reserved remark code). Bar width, pairing, and style are authoring preference, not spec - extend to any width that suits the file. Repeated bare markers (:::: / ....) also collapse to a single marker and serve the same visual-separator purpose.
:-------------------------------
:sect parsing
.title Parsing
.p The reference implementation (LsvRecord.cs) parses with a cursor rather than splitting the whole file up front. LsvRecord.Parsed(ref unparsed, out record) takes the remaining text by reference, returning false once no record remains - the natural shape for a while loop walking record-by-record. Within a record, fields walk the same way: cursor = 0; while (record.GotNextFieldValue(ref cursor, out value)). GotNextFieldNameAndValue(ref cursor, out name, out value) splits a raw field into name and value in one step.
.p Record / Context / Fields expose the raw record text, the trimmed header context, and the trimmed fields text respectively. Field values come back trimmed - surrounding CR/LF stripped.
.p This is a streaming, single-pass walk - not build-a-tree-then-query - consistent with the library's zero-allocation, minimal-heap-motion philosophy (see Chars, ItemStack).
:-------------------------------
:sect doc
.title DOC
.p DOC is one of LSV's reserved header-record typeCodes (see LsvDoc.cs) - the general-purpose document schema for captured or authored content (articles, notes, snippets, round-tripping with HTML/Markdown/PDF/Word). Reserved fields of a :DOC {id} record:
:def id
.of DOC
.means same value as the header directive (redundant, for validation)
:def title
.of DOC
.means required
:def author
.of DOC
.means author name(s)
:def url
.of DOC
.means source URL, if captured from the web
:def created updated captured
.of DOC
.means ISO 8601 timestamps
:def keywords
.of DOC
.means space-separated (quote multi-word phrases)
:def category
.of DOC
.means one of: article, documentation, reference, tutorial, recipe, blog-post, news, research, technical, creative, notes
:def format
.of DOC
.means original source format: html | markdown | text
:def codes
.of DOC
.means default <ref> for record codes used here but not defined by the schema - see aliasing
:def code
.of DOC
.means <code> <ref> - overrides .codes for one specific record code
:def chunks chunk
.of DOC
.means see chunking
:sect doc-extras
.title DOC - resources, content, local fields
.p A :DOC can also carry RESOURCE records (:img, :link, :colors, :layout, :meta - extracted references reused via <ref-*> placeholders) and CONTENT records (:frame, :summary, :abstract, :content - the body). The fuller catalog lives in the internal design notes (LSV-DOC.txt).
.p A :DOC isn't limited to its reserved fields - it may also carry locally-defined fields of its own, as long as they don't collide with the reserved names.
:-------------------------------
:sect aliasing
.title Record-code aliasing
.p A DOC's .codes <ref> declares, up in the header, where the document's record codes are defined; .code <code> <ref> overrides that default for one specific code. The <ref> is deliberately loose - an officially registered standard, a URL, or simply a description. Neither field is mandatory; undeclared codes remain plain local use. The point is efficient production: LSV is at heart a flat database where size is a factor, and a one-line pointer up top beats restating a code catalog in every file.
.p A field's value can optionally carry its own content type, declared via the :DOC's own attributes - the mechanism exists, but no content-type codes are specified yet (deliberately deferred; a field is plain text until designed further).
:-------------------------------
:sect chunking
.title Chunking
.p Any document type can be CHUNKED once it's too large for one physical file. Header field .chunks 0 = not chunked; .chunks n (n > 0) = split across n chunk files, where chunk 0 is metadata-only and chunks 1..n carry content; each chunk file's own header carries .chunk <n> saying which it is.
.p File naming (shown for DOC, same pattern for any chunked type): chunk 0 (meta only) = doc.{identity}.0; content chunk n = DOC.{identity}.{n}.lsv. A mismatch between filename and declared type/chunk invalidates the load - renaming a file is enough to take it "out of the loop" without touching its contents. Chunk 0's own .chunks value IS the max chunk number, so a reader can verify completeness by enumerating 1..n against the naming pattern.
:-------------------------------
:sect aidoc
.title AIDOC
.p Reserved header typeCode for documents GENERATED AND MAINTAINED BY AN AI, carrying that AI's own conventions in the AIDOC record's fields - the document tells its reader (human or another AI) how it is organized, rather than assuming a shared schema.
.p Typical shape: header :AIDOC <identity> <date> with an .about field, followed by a :schema record defining the file's own record types one line apiece. The header plus :schema make the file SELF-DESCRIBING: a cold session - or a different AI entirely - decodes the file from the file, no external schema registry required. Beyond that pattern, conventions are the authoring AI's to define per document; AIDOC reserves the space rather than fixing a schema.
.p This spec file is itself a :DOC - author-owned, AI-curated, carrying the standard interchange fields in its header. The AIDOC pattern is demonstrated by the AI's own working files behind this project (state digests, feedback ledgers, index maps) - so the format's two document schemas are both shown in live use.
:-------------------------------
:sect notes
.title Notes
.p LSV only defines SYNTAX; each record typeCode (DOC, CHAT, ...) defines its own SCHEMA on top. :DOC and :CHAT are the two schemas currently specified in the internal design notes (LSV-DOC.txt, LSV-CHAT.txt). :CHAT records a single human/AI conversation turn by turn (:msg {speaker}, .ref, .post) - a different schema on the same base syntax.
.p Nothing about LSV syntax requires a record's fields to match a predeclared schema - the parser only cares about markers and trimmed values. LSV also gets used informally as a lightweight structured-notes format: a typeCode invented on the spot, whatever fields make sense, no formal schema behind it. Schema conformance is a convention layered on top by whoever's reading the file, not something the format enforces.
.p csv can convert to an LsvDoc, have its fields reordered and/or renamed in code, then convert back out to csv - one vendor's column naming/order to another's. LsvDoc works as an editable intermediate for csv-to-csv vendor reformatting, not just a csv<->lsv format in itself.
